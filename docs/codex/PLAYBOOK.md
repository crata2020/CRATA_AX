# PLAYBOOK: CRATA 화면을 같은 느낌으로 만드는 법

업무사이트(`apps/worksite-next`)와 인사 앱(`apps/hr`)을 실제로 어떻게 만들었는지 정리한 문서예요. 그 과정을 다시 할 수 있게 순서대로 적었어요. `AGENTS.md`는 핵심 규칙만 담고 있어요. 이 문서는 그 규칙의 **이유, 정확한 값, 레시피, 실패 사례**를 담고 있어요.

**'같은 느낌'은 같은 모양이지, 같은 배치가 아니에요.**
- **모양(시각 언어)은 그대로 써요.** 토큰, 부품, 카드 머리, 숫자 무게, 차트 모양, 강조 하나, 문구 규칙. 한 제품처럼 보이게 하는 부분이에요(4장, 6장).
- **구성(어떤 요소를 어디에)은 화면마다 용도에서 새로 정해요.** 기준 화면과 레퍼런스는 어휘와 품질 기준이지, 베낄 배치가 아니에요(5.0).

| 장 | 언제 읽나 |
|---|---|
| 1. 어떻게 만들어졌나 | 처음 한 번 |
| 2. 만드는 순서 | 새 앱이나 새 화면 묶음을 시작할 때 |
| 3. Orbix 레퍼런스 읽는 법 | 레퍼런스 이미지를 받았을 때 |
| 4. 시그니처 요소 20개(4.0 복사할 파일 표) | 화면을 짜기 전과 다듬을 때 |
| 5. 화면 구성(5.0 용도 → 질문 → 요소 → 배치) + 출발점 레시피 8가지 | 새 화면을 짤 때 |
| 6. 느낌을 망치는 것 | 다듬을 때, 리뷰할 때 |
| 7. 내용 원칙과 예시 데이터 | 데이터와 문구를 만들 때 |
| 8. 검사 루프 | 화면마다 끝내기 전에 |
| 9. 여러 세션으로 나눠 맡길 때, 혼자 할 때 | 화면이 3개 이상일 때, 오케스트레이터 없이 한 세션으로 할 때 |
| 10. 앱별 참고 | 스토어, 동작, 사람 id가 필요할 때 |

## 1. 어떻게 만들어졌나

**한 줄:** 바탕(토큰·부품·차트·틀·데이터)을 먼저 만들고, 기준 화면 하나를 끝까지 다듬었어요. 그다음 화면별 브리프를 써서 여러 빌더에게 "자기 파일만" 맡겼어요. 품질은 스크린샷 비교 루프와 기계 검사로 지켰어요.

**반려에서 배운 것.** 처음에는 옛 Refine+antd 앱(`apps/worksite`)에 Orbix 껍데기를 씌웠어요. 검증을 5라운드나 했는데도 대표님이 반려했어요.

> "기존꺼는 아예 신경쓰지 말고 디자인은 인스타 자료 기반으로 새로, 내용은 리서치 기반"
> "오늘 할 일 카드가 예전 그대로"

옛 틀의 규칙(굵기, 그림자, 색 검사)이 새 스타일과 부딪혀서 덧칠로는 느낌이 나지 않았어요. 그래서 UI 라이브러리 없이 React 18 + TS + Vite + react-router(해시) + lucide-react + Pretendard만으로 바닥부터 다시 만들었어요. **새 화면도 옛 화면을 고쳐 쓰지 말고, 토큰 → 부품 → 기준 화면 순서를 따라 새로 만들어요.**

## 2. 만드는 순서

각 단계마다 무엇을 하는지, 왜 하는지, Codex에서는 어떻게 하는지를 적었어요.

### 2.1 리서치를 먼저 써요
- **무엇:** `docs/research/00~10`, 인사 앱은 `docs/hr/00_hr-direction.md`를 먼저 써요.
- **왜:** 화면에 들어갈 KPI 이름, 흐름 단계, 가드레일 문구를 지어내지 않으려고요. 브리프의 화면 명세에는 늘 "리서치 08: 수정 → 범위 분류 → 승인 → 규칙 → 효과"처럼 문서 번호를 근거로 달아요.
- **Codex:** 새 영역(예: 교육·자격)이면 화면보다 먼저 `docs/<앱>/<다음 번호>_<주제>.md`(예: `docs/hr/01_training-licenses.md`)에 근거 문서를 써요.
  - 받은 근거 자료가 없으면 출처를 지어내지 말고, 법 주기·대상 같은 값을 모두 "확인 필요"로 적은 초안을 써요. 화면에는 그 값을 "(예시)"로만 보여요.
  - `docs/research`, `docs/hr/00` 같은 문서가 저장소에 없으면(킷만 복사한 경우) 브리프의 근거 칸에 "없음, 확인 필요"라고 적고 진행해요.

### 2.2 레퍼런스를 모으고 이름을 붙여요
- **무엇:** Orbix 인스타 게시물 6장과 Dribbble 40장을 모았어요. 파일 이름은 설명형으로 바꿨어요. 예: `orbixcrm-projects-kanban-light.jpg`, `projectflow-grouped-task-table.jpg`.
- **왜:** 파일 이름이 브리프의 어휘가 돼요. "내 업무는 `projectflow-grouped-task-table.jpg`처럼"이라고 적을 수 있어야 모두가 같은 그림을 봐요.
- **Codex:** 이미지는 저장소 밖(스타일 묶음 zip의 `references/`)에 둬요. 프롬프트에는 경로만 주고 `view_image`로 열게 해요.

### 2.3 느낌을 규칙과 숫자로 바꿔요
- **무엇:** 레퍼런스 → 패턴 → 우리 적용 표를 만들고, 픽셀을 재서 라운드와 색 값을 뽑았어요. 최종값은 `docs/design/STYLE_GUIDE.md`에 있어요.
- **왜:** "느낌"이 규칙이 돼야 여러 세션이 같은 결과를 내요. 예: "짙은 덩어리는 화면당 하나", "큰 숫자는 굵기 500 + 증감 칩".

### 2.4 바탕을 이 순서로 만들어요(한 사람이)
1. `tokens.css`: 색 30개 + 차트 파스텔 14개, 라운드 6단계, 그림자 3개, 글자 크기 7단계, 틀 치수(사이드바 268, 상단 바 68, 간격 20/14)
2. `base.css`: 초기화. `ul, ol`을 함께 초기화해요. 빠뜨려서 한 번 고쳤어요.
3. `ui.css` + `ui/index.tsx`: 부품과 격자(`g-12`, `s-3`~`s-12`, `kpirow`, `kpigrid`, `tablewrap`)
4. `charts.tsx`: SVG를 직접 그려요(LineChart, CapsuleBars, Donut + Legend, Gauge, Heatmap, Sparkline)
5. `shell.css` + `Shell.tsx`: 흰 사이드바, 흰 상단 바, 900px 이하에서는 서랍 + 하단 탭
6. 라우트와 빈 페이지: 모든 화면을 `export default function Page(){ return <PageHead title="…" desc="준비 중" /> }` 두 줄로 먼저 만들어 둬요.

- **왜:** 부품이 먼저 있어야 화면 작업이 공통 파일을 건드리지 않아요. 빈 페이지가 있으면 라우트와 메뉴가 처음부터 다 살아 있어서, 화면 작업은 파일 하나만 채우면 돼요.
- **새 앱일 때:** 디자인 시스템을 **복사해서 그대로** 써요. 원본은 `apps/worksite-next/src/styles/{tokens,base,ui,shell}.css`와 `src/ui/{index,charts}.tsx`예요. 두 앱의 `ui.css`, `base.css`, `index.tsx`, `charts.tsx`는 한 글자도 다르지 않아요. `tokens.css`는 회사별 브랜드 블록(`:root[data-tenant=…]`)만, `shell.css`는 인사 앱의 `.navlink__n--live` 한 줄만 달라요. 그래서 두 앱이 한 제품처럼 보여요. 바꿔도 되는 건 브랜드 변수 4개뿐이에요. 앱 틀(설정 파일, `App.tsx`, `Shell.tsx`, 홈, 404)은 `docs/codex/starter/`에서 시작해요. 인사 앱의 `Shell.tsx`는 그 앱 데이터를 불러와서 그대로 복사하면 빌드가 안 돼요.

### 2.5 예시 데이터와 로직을 먼저 만들어요
- **업무사이트**
  - `types.ts` → 회사 데이터 `tr.ts`(제조), `crata.ts`(교육) → `format.ts`(md, dday, when …) → `store.tsx`의 `useApp()` 순서로 만들어요.
  - 주소로 회사와 사람을 바꿔요(`?tenant=tr|crata&as=<personId>`). 검사 스크립트가 여러 사람으로 화면을 볼 수 있게 하려는 거예요.
  - 실제 고객 이름은 `identity.ts` 한 파일에만 둬요. `vite.config.ts`가 `--mode public`일 때 이 파일을 `identity.public.ts`(가상 이름)로 바꿔 끼워요(`npm run build:public` → `dist-public`).
- **인사 앱**: 로직과 테스트를 먼저 만들어요.
  - `lib/model.ts`: CRATA 4종 어휘
  - `parse.ts`: 규칙 기반 "누구를 어디로" 해석
  - `fit.ts`: 적합도, 조언, 팀 분포(5명 이상)
  - `hiring.ts`: 서류 조건, 추천 등급, 면접 질문
  - `text.ts`: 조사
  - `engine.test.ts`: 테스트 14개
- **왜:** 숫자와 이야기가 맞아야 화면이 진짜처럼 보여요. 로직이 테스트로 고정돼 있으면 화면 작업은 화면만 신경 쓰면 돼요.

### 2.6 기준 화면 하나를 끝까지 만들어요
- **무엇:** 업무사이트는 홈(`Home.tsx`), 인사 앱은 인사이동(`Moves.tsx`)이에요. 레퍼런스와 나란히 놓고 여러 번 다듬었어요.
- **왜:** 브리프에 "이 화면과 **같은 품질·밀도·문법으로**"라고 쓸 실물이 있어야 해요. 글로 된 규칙만으로는 밀도가 맞지 않아요. 배치까지 같게 하라는 뜻은 아니에요. 인사 홈과 인사이동은 문법이 같지만 구성은 전혀 달라요(5.0).
- **Codex:** 새 앱이면 기준 화면을 먼저 하나 만들고, 사람이 확인한 뒤 나머지로 넘어가요(`PROMPTS.md`의 (2)).

### 2.7 화면별 브리프를 써요
- `SCREEN_BRIEF_TEMPLATE.md`를 채워요. 화면마다 레퍼런스 파일 이름과 가져올 부분, 위에서 아래로의 구성, 연결할 `act.*`, 리서치 근거, 지킬 문구를 적어요.
- 브리프 쓰는 요령은 이래요.
  - 레퍼런스는 **파일 이름 + 가져올 부분까지** 적어요. 어두운 레퍼런스라면 "밝게 바꿔서"를 붙여요.
  - KPI는 이름과 숫자 예시까지 정해 줘요(예: "고객 PPM 18, 목표 10").
  - 툴바 구성과 표 열은 순서대로 다 적어요.
  - 버튼은 스토어 함수와 묶어요(예: "'맞아요' → act.confirmSegment").
  - 권한·역할 경계와 다른 회사에서 보일 모습을 적어요.
  - 가드레일 문구는 문장 그대로 줘요.

### 2.8 화면 작업(자기 파일만, 자기 포트만)
- `src/pages/<Page>.tsx`, `.css`, `.parts.tsx`만 만들거나 고쳐요. `ui/ data/ shell/ styles/ lib/`와 `App.tsx`는 읽기만 해요. 오케스트레이터 없이 혼자 할 때 허용되는 줄은 9.1에 있어요.
- 첫 줄 주석에 레퍼런스를 적어요. 예: `// 내 업무: Orbix 'ProjectFlow' 상태별로 묶은 업무 표(refs/projectflow-grouped-task-table.jpg — 접는 그룹 머리, 색 네모 상태, 진행 막대 + %)`
- 개발 서버는 자기 포트로 띄워요.
- **왜:**
  - 파일이 겹치지 않아야 동시에 일해도 충돌이 없어요.
  - 포트가 다르면 서로의 서버를 끄거나 엉뚱한 화면을 찍지 않아요.
  - 첫 줄 주석이 있으면 리뷰할 때 "무엇을 보고 맞췄나"를 바로 알 수 있어요.

### 2.9 화면마다 도는 루프(2번 이상)
1. `npm run typecheck`로 내 파일 오류가 0인지 봐요.
2. 개발 서버를 내 포트로 띄워요. 그룹 id를 파일에 적어 두면 끌 때 이름으로 찾지 않아도 돼요.
   ```bash
   setsid sh -c 'echo $$ > .vite.pid; exec node node_modules/vite/bin/vite.js --port 4314 --strictPort' > .vite.log 2>&1 < /dev/null &
   ```
3. `node ../../scripts/ui-check.mjs --base http://localhost:4314/ --routes /<내 경로>,<관련 경로> --fold --a11y --out .ui-check/<Page>`(명령 끝에 다른 글자를 붙이지 않아요. 서버가 뜰 때까지 알아서 기다려요)
4. 결과가 `N shots, 0 with problems`(0 problems)인지 봐요.
5. `*.fold.png`와 레퍼런스, `docs/design/screenshots`의 비슷한 화면(같은 크기인 `<이름>.fold.png`)을 `view_image`로 나란히 열어요. 다른 점 목록(8.4)을 쓰고 고쳐요. **모양** 차이는 고치고, **구성** 차이는 용도(5.0) 때문이면 이유를 적고 그대로 둬요.
6. 3~5를 2번 이상 반복해요. 마지막 회차에는 `--flow`(2.11)로 클릭 뒤 상태도 찍어요.
7. 서버를 꺼요: `kill -- -"$(cat .vite.pid)" 2>/dev/null || kill "$(cat .vite.pid)"; rm -f .vite.pid`
   - `pkill -f`·`pgrep -f`로 찾지 않아요. 패턴(예: `vite --port 4331`)이 그 명령 줄 자체와도 맞아서, 대괄호 꼼수를 써도 복합 명령에서는 내 셸까지 죽어요(exit 144, 교육 화면 사례).
   - macOS처럼 `setsid`가 없으면 켜는 명령에서 `setsid`만 빼요. 끄는 명령은 같아요.

- **왜:** 기계 검사는 넘침과 오류만 잡아요. "Orbix 느낌"은 눈으로 비교해야 맞춰져요.

### 2.10 공통 문제는 한곳에서 고쳐요
- 화면 작업은 공통 파일 문제를 결과에 적기만 해요. 오케스트레이터가 모아서 한 번에 고치고, 그 뒤 **모든 화면**을 다시 검사해요.
- 실제로 이렇게 고친 것: `ol` 초기화, 모바일에서 flush 카드 여백, 선 차트 첫 x 라벨, 청록 브랜드 대비, 1024px에서 상단 검색 줄바꿈, 1단계 메뉴 숨김, 짧은 화면의 사이드바
- **왜:** 다섯 명이 각자 `ui.css`를 고치면 서로 덮어써요. 공통 부품이 바뀌면 다른 화면도 다시 봐야 해서 한 사람이 맡아야 해요.

### 2.11 동작 스크립트로 핵심 흐름을 눌러 봐요
- **업무사이트**
  - 현장 등록: 타일 → 한 줄 → 등록 → 목록 +1 → 품질 화면에서 배정

## 3. Orbix 레퍼런스 읽는 법

### 3.1 한 장을 읽는 순서
1. **'처음 보이는 것' 하나를 정해요.** Orbix 설명은 늘 "The first thing on the screen is …"로 시작해요. 우리 화면도 "이 화면에서 먼저 볼 것" 한 문장을 먼저 정해요. 예: 홈은 '이번 주 흐름 + 승인할 일', 인사이동은 '대화 + 조직도'.
2. **틀과 비율을 봐요.** 카드 칸 비율(8:4, 7:5, 3열, 4열), 간격과 패딩의 리듬을 봐요. 배치를 옮기려는 게 아니라 비율 감각을 익히려는 거예요. 목업 안에서는 크기가 바뀌어 있으니 px를 그대로 재지 말고 **상대 크기**로 옮겨요(예: KPI 숫자 34 : 라벨 13.5 ≈ 2.5 : 1).
3. **부품을 우리 키트에 대응시켜요.**
   - 알약 선택 → `PillSelect`
   - ⋯ → `MoreButton`
   - 증감 칩 → `Delta`
   - 아이콘 원 → `Kpi`의 `hue`
   - 회색 레인 → `.pj-lane` 문법
   - 키트에 없으면 화면 파일 안에 만들어요. 공통으로 올릴지는 오케스트레이터가 정해요.
4. **강조는 행동하는 곳에만 둬요.** 원문은 "Yellow only shows up where you act", "A green New Project button is the only loud element"예요. 우리는 짙은 버튼 하나 + `--brand`로 옮겨요.
5. **색은 전부 버리고 토큰으로 바꿔요.** 레퍼런스의 초록·보라·노랑은 `--brand` 하나, 상태색, 파스텔 7색으로 바꿔요.
6. **비교를 2번 이상 해요.** 화면마다 레퍼런스 1~3장을 정하고(`STYLE_GUIDE.md` 7장), 내 캡처와 나란히 봐요. 맞출 것은 모양(부품 생김새, 밀도, 위계, 강조 개수)이고, 배치는 이 화면의 용도로 정해요.

## 5. 화면 구성

### 5.0 구성은 용도에서 정해요(레시피보다 먼저)
레시피를 먼저 고르면 화면이 비슷해지고, 레퍼런스를 먼저 보면 그 배치를 따라가요. 그래서 **이 화면이 누구의 어떤 질문에 답하는지**부터 정해요.

우리 두 앱도 이렇게 만들었어요. 모양은 같지만 구성은 화면마다 달라요.

| 화면 | 용도 | 그래서 고른 구성 |
|---|---|---|
| 인사 홈 | 담당자가 주 1회 전체를 훑어요 | KPI 4 + 채용 흐름 + 팀별 인원 막대(최소 눈금) + 최근 확정 |
| 인사이동 | 사람을 옮겨 보며 일하는 작업 공간 | KPI 없이 대화 + 실시간 조직도. 확정 전 이동만 위에 |
| 공고 상세 | 많은 지원자를 골라 한 번에 처리 | 찾는 사람 + 추천 분포, 단계 탭 + AI 일괄 띠 + 묶음 표 + 서랍 |
| 지원자 검사 | 한 사람이 휴대폰으로 차분히 | 가운데 정렬 한 줄 흐름, 장식 배경(이 화면만) |
| 업무사이트 홈 | 오늘 눌러야 할 것 | 이번 주 흐름 + 승인할 일 3줄이 첫 화면 |
| 프로젝트 / 회의 | 상태를 옮기며 관리 / 하나씩 확인 | 칸반 / 목록 + 상세 |

**순서**
1. **일:** 누가, 언제, 어떤 기기로, 이 화면에서 무엇을 결정하거나 끝내나(브리프 1장).
2. **질문:** 그 사람이 화면을 열며 묻는 질문을 3~5개 적고 순서를 매겨요. 예: "오늘 내가 처리할 건?" > "어느 팀이 모자라지?" > "지난달보다 나아졌나?"
3. **요소:** 질문마다 답의 모양을 보고 요소를 골라요(아래 표). 차트부터 정하지 않아요. 답이 숫자 하나면 KPI, 많은 항목을 골라 처리하면 표예요.
4. **배치:** 1번 질문의 답과 그 행동이 첫 화면(1440×1000, 390×844)의 왼쪽 위에 와요. 주인공은 큰 칸(8·7), 보조는 작은 칸(4·5). 행동은 근거 바로 옆에 둬요.
5. **빼기:** 어느 질문에도 답하지 않는 카드는 빼요. 레퍼런스에 있다고, 칸이 비었다고 더하지 않아요.
6. **구성안 2개:** 짜기 전에 텍스트 와이어프레임으로 2개를 쓰고(위에서 아래로 카드 이름 · 칸 비율 · 답하는 질문 번호), 1번 질문에 더 빨리 답하는 쪽을 골라요. 사람이 대화 중이면 고르게 해요.
7. **출발점:** 아래 레시피 A~H 중 가까운 것을 출발점으로 써요. 맞지 않으면 섞거나 새로 짜고, 이유를 브리프에 적어요.

**질문 → 요소**

| 질문(답의 모양) | 쓸 요소(우리 부품) | 피할 것 |
|---|---|---|
| 지금 내가 처리할 건?(결정할 몇 건) | 승인 목록 3~4줄 + '나머지 n건 보기', AI 일괄 띠 + 짙은 버튼 | 숫자만 보여 주고 행동은 다른 화면에 |
| 이 숫자가 괜찮나?(값 + 비교) | `KpiCard`·`Kpi` + `Delta` + '그래서' 한 줄 | 비교 없는 숫자, KPI 6개 이상 |
| 시간에 따라 어떻게 변하나?(추세) | `LineChart`(연속), `CapsuleBars`(기간별 양, 강조 하나), KPI 옆 `Sparkline` | 점이 몇 개 안 되는 선, 축 숫자가 빽빽한 차트 |
| 무엇으로 나뉘나?(구성비) | `Donut` + `Legend`(5개 이하), `StackBar`(한 줄 비율) | 조각 6개 이상 도넛(→ 막대 목록) |
| 기준보다 모자란 곳은?(기준 대비) | 최소 눈금 막대 목록(`.hh-heads`), `Gauge`(목표 하나) | 숫자만 늘어놓은 표 |
| 어느 단계에 얼마나?(흐름) | 단계 흐름 띠(`.hg-flow`), 직접 옮기며 일하면 칸반 | 파이 차트 |
| 많은 항목을 훑고 골라 처리 | 툴바 + 묶음 표 + 서랍 | 카드 격자(줄끼리 비교가 어려워요) |
| 사람·팀을 둘러보기, 구조 바꾸기 | 카드 격자(사람 중심), 조직도(구조·이동) | 긴 표 |
| 언제 무엇이 있나? | 달력 '보기' + 날짜 머리 일정 카드, 타임라인 | 일정 편집 도구를 새로 만들기 |
| 언제·어디에 몰리나?(두 축 분포) | `Heatmap` | 3D, 버블 차트 |
| 말로 지시하고 결과를 본다 | 대화 + 결과 패널(D) | 폼 여러 개 |
| 설정·입력 | 구역 폼 + 오른쪽 상태 열(E) | 한 장짜리 긴 폼 |
| 개인·민감·차분한 일 | 가운데 화면(G) | 대시보드 격자 |

**배치 원칙**
- 첫 화면에 '결정 하나 + 그 근거 + 그 행동'이 다 보여요. 스크롤해야 보이는 주 동작은 다시 봐요.
- 개요 화면(홈)은 넓게 훑어요(KPI + 요약 카드). 작업 화면은 한 일에 집중해요(KPI는 없거나 3개 이하).
- 같은 데이터라도 쓰는 사람이 다르면 구성이 달라요. 현장(모바일, 매일)은 맨 위에 행동, 관리자(PC, 주 1회)는 맨 위에 요약.
- 차트는 화면당 2~3개까지, 차트마다 질문 하나에 답해요.
- 'KPI 4장 + 차트 2개 + 표 1개'는 어느 화면에나 맞는 공식이 아니에요. 용도와 맞을 때만 써요.

**구성안 예(교육 · 자격):**
```
구성안 1(일괄 처리 중심): [KPI 3: 만료 지남 · 30일 안 · 최소 미달 팀] / [s-8 만료 묶음 표 + 일괄 띠] [s-4 다가오는 회차]
구성안 2(팀 위험 중심):   [KPI 4] / [s-8 팀별 유효 인원 막대(최소 눈금)] [s-4 다가오는 회차] / [s-12 탭 + 일괄 띠 + 묶음 표]
→ 2를 골라요. 담당자의 첫 질문이 "어느 팀이 모자라지?"이고, 표는 그다음에 고르는 곳이라서요.
```

### 5.1 출발점 레시피 8가지

## 7. 내용 원칙과 예시 데이터

### 7.1 내용 원칙 15가지(근거 문서)
1. **홈은 "오늘 내가 눌러야 할 것"으로 시작해요**(대표님 피드백, 06 문서 6.3)
   - 승인할 일은 6종류예요: 승인, 분류 맞아요, 업무로 만들기, 확정, 배정, 반영.
   - 한 건은 한 사람 홈에만 보여요.
   - 카드에는 3~4건만 보이고, 없으면 '다가오는 내 업무'로 바뀌어요.
2. **입력은 연동·AI·규칙이 먼저 채워요**(06)
   - 제조 1단계에서 사람이 손으로 쓰는 것은 현장 등록 한 줄과 클레임뿐이에요.
   - 현장 등록은 큰 타일 4개 + 60자 한 줄 + 최근 위치 칩으로 끝나요.
3. **AI는 제출·추천까지, 완료·결정은 사람이 해요**(09, HR 3.2)
   - 'Claude로 제출 · 07:55'는 보이지만, '완료'는 검토자가 웹에서 해요.
   - AI 연결 기록에 차단된 줄이 있어요.
4. **근거와 확신도를 붙여요**(02 6.1~6.2)
   - 0.85 이상은 자동으로 붙여요.
   - 0.60~0.84는 확인 카드로 보여요.
   - 0.60 미만은 미분류예요. 미분류는 실패가 아니에요.
   - 인사 로직은 규칙 기반 + 테스트예요. LLM은 문장만 다듬어요.
5. **숫자에는 단위, 비교 기준, '그래서' 한 줄이 붙어요.** 숫자는 다른 기록에서 계산해요(PPM = 부적합 수량 ÷ 출하 수량).
6. **약속은 측정할 수 있는 것만 해요**(00, 08)
   - 같은 수정 재발률 46→19%, PPM 42→18(목표 10)처럼 좋아지지만 완벽하지 않게 보여요.
7. **사업 > 프로젝트 > 파트가 뼈대예요**(00 4장, 03 L6)
   - 프로젝트 코드에 모든 것이 붙어요.
   - 사업 색은 어디서나 같아요.
   - 출처 칩이 붙어요.
   - 진단 전 구조에는 '가설'을 표시해요.
8. **데이터 등급이 화면에 보여요**(04)
   - L1·L2 칩을 달아요.
   - 등급별 경로를 보여 줘요.
   - L2 문서의 해외 경로 요청은 차단 사례로 보여요.
   - L3는 처리하지 않아요.
9. **개인 영역은 기본 비공개예요.**
   - ARA: 10명 이상 월 단위 집계만 가요. '일하는 방식 카드'는 문장마다 '팀에 공유' 토글이 있고, 기본은 꺼져 있어요.
   - CRATA: 본인만이 기본이에요. 팀 분포는 5명 이상일 때만 보여요.
   - 두 임계치를 섞지 않아요.
10. **채용의 법 기준은 문구와 폼 필드로 지켜요.**
    - 정책은 `/policy`에 모아요.
    - 기준이 걸리는 화면에도 한 줄로 반복해요.
11. **복지 문구는 의료 표현을 쓰지 않고, 위기 안내를 넣어요**(10 5장)
    - 대신 쓰는 말: 성향 프로파일, 자기이해 코칭, 고민 정리, 전문 상담 연결

    - 메일 클라이언트, 문서 에디터, STT, 범용 PM, 사내 검색, 발령·급여는 만들지 않아요.

14. **회사·역할마다 다르게 보여요.** 맞지 않는 화면은 정직한 빈 화면으로 보여요.

    - "관리자만 볼 수 있는 화면이에요"

### 7.3 예시 데이터 만드는 순서
1. **이야기 시트를 먼저 써요.**
   - 회사 한 줄(예: `예시정밀산업 · 자동차 부품 제조 · 47명`)
   - 등장 역할
   - 관통하는 사건 2~3개
   - TODAY
2. **실제 고객 이름은 identity 파일 하나에만 둬요.** 거래처는 `예시배기시스템(주)`처럼 '예시'로 시작해요.
3. **사람 이름은 앱 성격에 맞춰요.** 업무사이트는 역할 코드(`공장장(예시)`)를 쓰고, 인사 앱은 가상 한국 이름을 써요.
4. **날짜 기준은 앱마다 하나예요.** `format.ts`의 `dday`, `when`으로 계산하고, 렌더링에서 `new Date()`를 쓰지 않아요.
5. **한 사건이 여러 화면을 꿰뚫게 해요.** 예: 클레임 `CL-2026-03`이 프로젝트, 업무, AI 실행 기록(L2라 8D 초안 차단), 산출물, 8D 단계, 도입 단계에 같은 숫자와 상태로 나와요.
6. **숫자는 그럴듯하게 만들어요.**
   - 좋아지지만 완벽하지 않게 해요.
   - 주말에는 일이 적어요.
   - 건강도는 good·warn·risk를 섞어요.
   - 확신도는 0.5~0.85, 점수는 넓게 퍼뜨려요(결정적 난수).
7. **모든 UI 상태에 예시를 최소 1건 둬요.** 막힘, 미분류, 차단된 AI 실행, 초대만 된 사람, 동의 안 함, 5명 미만 팀, 최소 인원과 같은 팀, 마감된 공고, 검사 전 지원자.
8. **화면 숫자는 저장된 데이터에서 계산해요.** 예: `store.tsx`의 `approvals`, 인사 앱의 `world()`.
   - 다른 화면과 이어지는 사건(확정 전 이동, 지원자, 클레임)은 store에 있는 것만 써요. 첫 화면에서 store에 그 사건이 없으면 그 그룹은 빈 문장("확정 전 이동이 없어요. 인사이동에서 정하면 여기에 올라와요")으로 둬요. 이 화면에서만 '검토 중(예시)' 이동을 지어내면 홈·인사이동의 '확정 전 이동 0'과 어긋나요(교육 화면 사례). 필요하면 seed에 넣을 값을 보고의 '공통 파일에서 고칠 것'에 적어요.
   - 이 화면에만 있는 기록(교육 만료일, 회차처럼 아직 seed에 없는 것)은 화면 예시 데이터로 둬도 돼요. 대신 seed의 사람·자격과 1:1로 맞추고(테스트로 고정), 화면에 '(예시)'를 붙여요.
9. **'예시'를 여러 겹으로 표시해요.** 파일 첫 줄 주석, 이름 뒤 `(예시)`, 토스트, 화면 작은 글씨, '가설' 표시.
10. **피할 것**
    - lorem, Acme, John Doe, 'Task 1'
    - 공개 빌드에 실제 이름 넣기
    - L3 데이터
    - 모두 초록인 KPI, 둥근 숫자만 있는 데이터
    - 진행 중인데 진행률 0
    - 화면마다 따로 적은 숫자
    - 지난 목록의 미래 날짜

`ui-check` 사용법은 파일 머리 주석(`node scripts/ui-check.mjs --help`)에 있어요. 경로 파일은 `scripts/routes.hr.json`과 `scripts/routes.worksite.json`(회사 × 사람 변형, 작업자는 모바일 3화면만)이에요. 클릭 흐름 예는 `scripts/flows/`에 있어요.

**기계 검사가 헷갈릴 때**
- **OVERFLOW를 읽는 법:** `범인:` 뒤의 요소부터 봐요. 표 칸처럼 `.tablewrap` 같은 스크롤 상자 안에 있는 요소는 넘쳐도 잘려서 범인이 아니에요. 범인이 `absolute`로 표시되면 기준 상자가 스크롤 상자 밖이라 빠져나간 거예요. 예: base.css `.sr-only`(left·top 없음)를 `<th>` 안에 쓰면 390px에서 페이지가 넓어져요 → `aria-label`로 바꿔요. 범인을 못 찾았다고 나오면 `report.json`의 `wide`와 `culprits`를 같이 봐요.
- **명령이 exit 2로 끝나요:** 인자 오류예요. 명령 끝에 붙은 `.` 같은 글자를 지우고, 경로는 `--routes` 뒤에 쉼표로 붙여요.
- **playwright를 못 찾아요:** 이미 깔린 곳이 있으면 `PW_MODULE=/…/node_modules/playwright-core`(폴더 경로)와, 브라우저가 기본 위치에 없으면 `CHROMIUM_PATH`를 줘요. `PLAYWRIGHT_BROWSERS_PATH`가 잡혀 있으면 `CHROMIUM_PATH`는 없어도 돼요. 없으면 처음 한 번 저장소 루트에서 `cd scripts && npm ci && npx playwright install chromium`(ui-check는 앱 폴더 → `scripts/node_modules` 순서로 찾아요).
- **콘솔 오류가 글꼴 403(`/@fs/…/pretendard…woff2`)이에요:** `node_modules`가 저장소 밖을 가리키는 심볼릭 링크라 Vite가 막은 거예요. 화면 문제가 아니라 환경 문제예요. 앱 폴더에서 `npm ci`로 진짜 설치를 하고 다시 찍어요. 그래도 안 되면 보고에 적어요(`vite.config.ts`는 공통 파일이에요).

### 8.2 캡처 요령(`view_image`로 볼 때)
- **비교는 `*.fold.png`(뷰포트 캡처)끼리 해요.** 기준 캡처도 `docs/design/screenshots/**/<이름>.fold.png`가 같은 크기로 있어요. 전체 캡처는 긴 변 2048px 안으로 크게 줄어들어 디테일이 사라져요. 아래쪽을 봐야 하면 해당 영역을 잘라서 봐요. `hr/applicant-drawer.png`는 그 자체가 1440×1000 첫 화면이라 fold 파일이 따로 없어요.
- 화면마다 새 브라우저 컨텍스트를 써요. 스토어가 메모리라서 앞 화면의 상태가 남지 않게 하려는 거예요(`ui-check`가 그렇게 해요).
- 전체 캡처에서는 `position: fixed`(하단 탭, 토스트)가 페이지 중간에 찍혀 보여요. 착시니까 fold로 판단해요.
- 서랍처럼 긴 패널은 스크롤하며 여러 장 찍어요.
- 주 동작이 접는 선 위에 있는지는 fold로 봐요.

- **오케스트레이터 하나**(사람 또는 Codex 세션)가 바탕, 기준 화면, 브리프, 공통 수정, 전체 검사를 맡아요.
- **화면 세션**에는 브리프의 화면 한 절씩 줘요. 규칙은 이래요.
  - 내 파일만 고쳐요.
  - 내 포트를 써요(worksite 4302~4305, hr 4312~4315). 서버는 `.vite.pid`로 끄고 `pkill -f`를 쓰지 않아요(2.9).
  - 첫 줄에 레퍼런스 주석을 달아요.
  - 공통 문제는 보고만 해요.
  - 새 패키지와 커밋은 금지예요.
- 같은 폴더에서 동시에 쓰면 충돌하기 쉬워요. 화면 세션마다 git worktree를 따로 쓰거나, 파일이 겹치지 않게 나눠요. 서브에이전트를 쓸 때도 같아요.
- 결과 보고 형식: 바꾼 파일, `ui-check` 결과 줄, fold 캡처 경로, 남은 다른 점, 승인 전 가정, **공통 파일에서 고칠 것**
- 공통 수정이 들어가면 모든 화면에 `ui-check`를 다시 돌려요.
- 포트: hr 4311(기준 서버)·4312~4315(세션), worksite-next 4301·4302~4305, 새 앱 4321~. 과제가 다른 포트를 정하면 그걸 써요.

### 9.1 혼자 작업(오케스트레이터 없음)
한 세션이 새 화면 하나를 처음부터 끝까지 맡으면, 라우트와 메뉴를 더할 사람이 없어요. 이때는 규칙을 어기지 않고 끝낼 수 있게 아래만 허용해요.

| 허용 | 범위 |
|---|---|
| `src/App.tsx` | 라우트 1줄 |
| `src/shell/Shell.tsx` | 사이드 메뉴 1줄 + `PAGE_TITLE` 1줄. 하단 탭(`.tabbar`, 4개)에는 넣지 않아요 |
| 새 파일 `src/lib/<page>.ts` | 계산 함수 + 이 화면만 쓰는 예시 데이터(seed의 사람·자격과 1:1로 맞춰요) |
| 새 파일 `src/lib/<page>.test.ts` | `node:test`. `npm test`(`src/lib/*.test.ts`)가 같이 돌려서 DoD에 들어가요 |

- 기존 공통 코드(`src/ui`, `src/styles`, `src/data/seed.ts`, `src/data/store.tsx`, 기존 `src/lib/*.ts`)는 고치지 않아요.
- 스토어에 없는 상태(예: 교육 일정 잡기)는 화면 `useState`로 둬요. 다른 화면에 다녀오면 사라져요. 보고의 '공통 파일에서 고칠 것'에 store 함수 이름과 인자를 적어요(예: `act.bookTraining(ids, sessionId)`).
- 새 공통 타입(예: 자격별 최소 인원 `licenseMin`)이 필요하면 있는 값으로 대신하고(예: `Team.min`), 화면 주석과 보고에 "대신 썼어요"라고 적어요.
- 바꾼 공통 줄은 보고에 그대로 붙여요. 셸을 바꿨으니 전 경로 `ui-check --routes @../../scripts/routes.hr.json --fold --a11y`를 다시 돌려요.
- 브리프 확인: 사람이 대화 중이면 초안을 보여 주고 기다려요. 무인 실행이면 `docs/codex/briefs/<page>.md`(과제가 다른 위치를 정하면 거기)에 쓰고 바로 진행하고, 판단한 것은 '승인 전 가정'에 적어요.
